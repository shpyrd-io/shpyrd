A project made from the catalog is now pinned to a **version** of its entry: the entry's folder together with the commit of the code, resolved when the catalog was published. Nothing reads the upstream branch, so a new commit upstream changes nothing by itself.

When the catalog publishes another version, the project says so. On its Summary, the **Catalog** card shows the version it runs and, when there is one, the update on offer: what applying it does, a field for each new input, and an **Update** button. From the terminal, `shpyrd catalog status <project>` shows the same and `shpyrd catalog update <project>` previews, asks and applies. An update only adds: it keeps every config var, plain variable, replica count and size the project has, never overwrites a value a person set, and removes nothing. A variable the project already has keeps its value whatever the new version declares; only variables it lacks are added, and the preview names both. A new generated input is generated, a new one with a default takes it, and a new required one must be given.

Each release of a project records the version it runs, so a rollback returns to the older version and the update is offered again. A rollback restores the build, the config vars, the sizes and the attachments of the release, but not the entry's process definitions, the build settings or the plain variables the update added, and it does not remove what the update created. Applying the update again takes back the values the project had for the config vars the rollback removed, so a generated key is not generated twice.

Servers that run the controller need the App definition of the same version: apply the manifests that ship with it. Automatic updates are not available. See [Updating a project from the catalog](/docs/deploying#updating-a-project-from-the-catalog).
